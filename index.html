I didn't come to technology through a computer-science degree. I came to it through operations — starting with a national assessment program in public education, where I helped pilot and deploy a Computer-Based Testing system still in use today, and continuing through the queues, the paperwork, and the verification requests that come with running licensure and registration services at the Professional Regulation Commission.

Somewhere in that work, I started noticing the same pattern: a process that could clearly be simpler, if only the right small system existed for it. So I started building those systems myself — first in spreadsheets and Apps Script, later with proper databases and real-time infrastructure — using vibe coding to close the gap between an operational idea and a working prototype.

I'm not trying to become a full-time software engineer. I'm an operations leader who happens to build — and who's found that the two disciplines make each other sharper.

03 — What I Build

Problem-first, vibe-coded, tested in the real workflow.

Every system I've built started the same way: something at work was slower, more error-prone, or more paper-dependent than it needed to be — and no one was going to fix it unless I did.

I build by vibe coding — directing an AI coding system (I use Claude) toward a specific operational problem, reviewing and testing everything it produces against how the work actually happens, and iterating until the system holds up under real use, not just in a demo.

I don't come from a traditional computer-science background. What I bring instead is the operational judgment to know which problems are worth solving, and the persistence to get a vibe-coded build from prototype to something my colleagues actually rely on.

What "vibe coding" means here

  • AI-directed, human-reviewed — not autogenerated and shipped blind
  • Built for one real workflow at a time, not a generic demo
  • Tested by the people who'll actually use it, before anything is called "done"

04 — Featured Work

Two systems, still in active use, that started as personal initiatives.

Vibe-coded electronic queue management

Project Queue+

Live · Adopted office-wide
Client→ Ticket→ Counter→ Display board

All four reflect the same queue state in real time.

  1. The problem

    Walk-in clients at PRC Region III's service counters queued manually, with no way for staff or clients to see wait status, and no live coordination between the ticketing desk, processing counters, and the public display board.

  2. Constraints

    No dedicated software budget or engineering team — this was self-directed work fit around a full-time operations role, built with tools already available in a government office before there was a case to justify anything more.

  3. The idea

    A low-cost electronic queueing system built first inside tools the office already trusted, with a path to upgrade the backend once the idea proved itself.

  4. The system

    Client-facing ticket generation, a staff processing console, and a live public display board with voice announcements — all reflecting the same queue state in real time.

  5. Implementation

    Started on Google Apps Script and Sheets to prove the workflow at zero infrastructure cost, then migrated the backend to Supabase (Postgres) for real-time sync once it needed to handle live, concurrent updates across ticketing, counters, and the display board reliably. Deployed on Netlify.

  6. Results

    Piloted in July 2026 and, after proving itself in daily use, formally adopted office-wide by memorandum. A technical report and research manuscript documenting the system are in development.

  7. What I learned

    Adoption in a government office depends as much on trust and fit with the existing workflow as on the technology itself — proving the idea cheaply, in the actual environment, mattered more than building the "best" version first.

Verification & inter-agency workflow

PRVS — Professional Records Verification System

In active use
Submit request→ Verify & coordinate→ Certificate issued

Status is tracked end-to-end, with a 30-second auto-refresh.

  1. The problem

    Verifying PRC-issued credentials for law-enforcement requests (PNP Anti-Cybercrime Group) ran through manual, paper-based coordination between agencies — slow, hard to track, and easy to lose status on.

  2. Constraints

    The system needed to work across two separate agencies' staff, handle document uploads securely, and fit within tools already available rather than requiring new agency-wide procurement.

  3. The idea

    A shared verification portal where officers could submit a request per individual, attach the required documents, and track status end-to-end, replacing the paper trail with a single system of record.

  4. The system

    Per-request submission and document upload, status tracking with a 30-second auto-refresh, a built-in "Ask PRC" messaging thread tied to each request, and certificate issuance tracked by issuing office.

  5. Implementation

    Built on Google Apps Script and Sheets with a custom HTML/CSS/JS front end — chosen to fit inside existing government-approved tooling and minimize procurement friction.

  6. Results

    In active use for inter-agency credential verification between PRC and PNP ACG.

  7. What I learned

    A system doesn't need a "modern" stack to be genuinely useful — it needs to fit the workflow and the constraints of the organizations actually using it.

  • Apps Script
  • Google Sheets
  • HTML/CSS/JS
